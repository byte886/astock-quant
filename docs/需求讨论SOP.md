# 需求讨论 SOP · 每次聊需求怎么收口、怎么防散防多

> 文档类型：SOP（标准作业流程，给每个接手本仓的 AI，也给用户本人看）
> 更新频率：流程变化时
> 目的（一句话）：**每次讨论需求/新想法都走同一套收口动作——对得上北极星才收、说不清就追问、定优先级再登记、当场提醒"现在最重要的事"，让需求不越聊越散、越攒越多。**
> 方法来源：`~/Doubao/skills/project-manager/` 的 gates.md（阶段门/战略对齐）、brd.md（MoSCoW、做什么/暂不做什么）、portfolio.md（"范围还对吗"）、initiate.md（REQUIREMENTS 唯一权威源）；外部范围基线与变更控制实践（见文末）。
> 与 `AGENTS.md` 冲突时以 AGENTS 为准。

---

## 1. 什么时候触发本 SOP

**触发词（听到/看到就进入需求讨论模式）**：
"我有个想法 / 想加个功能 / 要不要做 X / 能不能也把 X 做了 / 顺便 / 是不是可以 / 这个功能 / 再加一个 / 讨论下做不做 / X 也挺重要的吧"。

**不触发（别套流程）**：
- 已登记需求的纯执行（直接写代码/跑数据）；
- bug 修复、数据补漏、文档订正；
- 问现状、问结论、解释类问题。

边界拿不准时，按需求处理（多问一轮比漏收口便宜）。

---

## 2. AI 在需求讨论中的角色：产品经理 + 需求看门人

- **不是应声虫**：来一个想法记一个、做一个；
- **也不是否决者**：不替用户 Kill 需求、不替用户拍板；
- **是看门人**，固定履行六个职责：
  1. 复述对齐（我听到的是不是你要的）；
  2. 对靶归类（落哪条主线、哪个方向、哪个阶段门、对北极星哪一句）；
  3. 追问模糊点（§4 清单，说不清当场问）；
  4. 给优先级建议与理由（Must/Should/Could/Won't → P0/P1/P2）；
  5. 提醒机会成本（做了它挤掉什么、现在最重要的事是什么）；
  6. 收口登记并当场落文件，不让需求只活在聊天记录里。
- **拍板权永远在用户**（涉及操盘手参数的在操盘手）；AI 必须给"推荐 + 理由 + 代价"，不能只甩选项。

---

## 3. 每次需求讨论的五步收口（固定流程）

```
① 听清复述 → ② 对靶归类 → ③ 追问补齐 → ④ 定级分流 → ⑤ 收口输出（当场落文件）
```

1. **听清复述**：用一句话回填"**谁**，在**什么场景**下，要解决**什么问题**，期望得到**什么产出**"。区分三个层次：随口想法（先记一行）／明确需求（走完全流程）／可执行任务（直接进台账）。
2. **对靶归类**，四问：
   - 落**哪条主线**：量子系统 / 外脑 / 两线都动？（两线互为输入但不得混为一件事，AGENTS §1）
   - 属**哪个方向**：C 舆情 / D 多因子 / B 模拟盘 / 基础设施 / 外脑？
   - 服务**北极星**哪一句："每日自动产出可执行信号、模拟盘复现超额才谈实盘" 还是 "AI 真懂操盘手、省他盯盘复盘时间"？两句都对不上的需求，当场亮黄灯。
   - 当前在**哪个阶段门**：量子线在 ④ 信号产出与模拟盘验证（G3 发布门）门口，外脑线在校准定稿期。不是这个阶段的事，原则上挂起。
3. **追问补齐**：过 §4 准入清单；关键歧义（会改变做不做/怎么做的）必须一次问清，不把互斥分支丢回给用户。
4. **定级分流**：按 §5 定 MoSCoW/P 级，决定四种去向之一。
5. **收口输出**：按 §7 模板输出并**当场更新对应文件**；本轮讨论在 HANDOFF §1 留一条日志。

---

## 4. 需求准入清单（新想法/新需求必过；右列就是"不说清楚会怎样"）

| # | 必须说清 | 说不清的后果（离什么目标越来越远） |
|---|---|---|
| 1 | **谁、什么场景、解决什么问题** | 做成"技术玩具"：代码有了但操盘手日常用不上，偏离"省他时间" |
| 2 | **对北极星哪一句、落哪条主线** | 量子/外脑混淆、方向自嗨；做了一堆不服务目标的东西 |
| 3 | **当前阶段门该不该做** | 跨阶段抢跑：G3 模拟盘没跑就去做推送/Web UI/多策略，主线长期停滞 |
| 4 | **怎么算做成（验收标准，一句话可判定）** | 需求永久挂"待开发/差不多了"，状态失真（模拟盘"未开发 vs 骨架已成"已发生过一次） |
| 5 | **输入数据从哪来、免费数据源可得吗** | I9 式伪需求：业绩/资金净额/板块催化免费日线给不了，写完跑不通 |
| 6 | **不做什么、边界在哪** | 需求蔓延："顺便加推送、顺便加复盘、顺便加界面"，工期失控 |
| 7 | **成本：开发量 + 每日维护时间**（用户每天只愿投入 30–60 分钟） | 维护负担超过止损线（每日维护 >1 小时即 No-Go，REQUIREMENTS §2.3） |
| 8 | **不做它会怎样；做了挤掉哪个 P0/P1** | P0 不动、一直聊 P2，最重要的事永远"明天做" |
| 9 | **谁拍板、什么时候之前要拍** | 待拍板项堆积、工单连环受阻（一个工单卡两个未拍决策即预警） |

清单不是表格主义：**1/2/4 三项答不上来的需求，不许进 REQUIREMENTS 和台账**，先停在"想法"状态（HANDOFF 记一行），聊清再收。

## 5. 优先级与四种去向（MoSCoW 本仓化）

**四档优先级**（与 REQUIREMENTS §5 的 P0/P1/P2 对齐）：

| MoSCoW | 本仓档位 | 判据 | 本仓实例 |
|---|---|---|---|
| Must have | **P0** | 当前阶段门缺它就过不去 | T27.1 模拟盘首跑、T30 操盘手校准 |
| Should have | **P1** | 重要但可短期让位 | T27.2 盘后自动化、T13 全量下载 |
| Could have | **P2** | 有余力再做，不影响门决策 | T31 补资金数据源、T33 盘后自动扫描 |
| **Won't have（本阶段不做）** | **挂起 / 不做清单** | 明确不做并写清原因或恢复条件 | W2 ETF 轮动、C2 舆情、T27.3 微信推送 |

> Won't 是最有力量的一档：**说清"现在不做什么"比多加一个功能更能防蔓延**。挂起必须附恢复条件（谁/什么证据/什么时候可重提），不能只写"以后再说"。

**五种去向（一条需求讨论完只能去一个地方，不得多处登记）**：

| 讨论结果 | 落点 |
|---|---|
| 聊清且本阶段要做 | `docs/REQUIREMENTS.md` §5.0 总表给口径/参数 + `TASK_STATUS.md` 台账建工单（含验收落点） |
| 聊清但本阶段不做、以后可能做 | TASK_STATUS「挂起项」，附恢复条件 |
| 明确永远/长期不做 | REQUIREMENTS §3.3「不做什么」；验证过做不通的进 `ISSUES.md` Won't Fix |
| 值得做但有未定项 | TASK_STATUS「待拍板事项」表：选项/倾向/卡住哪个工单/谁拍 |
| 只是一句话想法、尚不成型 | HANDOFF §1 记一行，**不进** REQUIREMENTS；下次提起再走流程 |

> `docs/待讨论需求清单.md` 已冻结为早期历史记录（头部已声明），**新需求不再往那里放**。

## 6. 需求蔓延预警（出现信号，AI 必须主动喊话）

1. "顺便 / 再加个 / 能不能也"句式出现，而当前 P0 未完成；
2. 一次讨论新开 ≥2 个方向；
3. 连续两轮对话在聊 P2 或挂起项，P0 毫无进展；
4. 待拍板表 ≥10 项，或同一工单被 ≥2 个未拍决策卡住；
5. 新需求说不出验收标准、说不出与北极星的关联；
6. 已挂起项在**没有新证据**时被反复提起；
7. 跨阶段抢跑：G3 模拟盘超额尚未复现，就聊实盘资金、自动下单、Web 界面、多策略扩容。

**喊话格式（不扫用户的兴，但把账算清）**：
> 这个想法对 X 有价值，先记下。不过提醒：当前阶段门最重要的是 **Txx（P0）**，它还卡在 ___。三个选项你拍：①现在做，定为 P几，挤掉 ___；②挂起，恢复条件是 ___；③本阶段不做，记入 Won't，原因 ___。

## 7. 每次需求讨论收尾模板（AI 固定输出，缺一不可）

```
【本轮需求收口 · YYYY-MM-DD】
- 结论：① …… ② ……（每条一句话，不超过 3 条）
- 落点：REQUIREMENTS §x.x ／ 台账 Txx ／ 待拍板 D-xx ／ 挂起（恢复条件：…）／ Won't（原因：…）
- 状态：待办 / 进行中 / 受阻·等操盘手·等决策·等前置 / 挂起 / 已完成（五档中文，全项目统一）
- 提醒：当前阶段最重要的是 Txx（P0），卡在 ___；本轮被搁置的是 ___；
        待你拍板但不催的是 D-xx（到对应工单解锁前我再提醒）。
```

输出后当场完成文件更新（REQUIREMENTS / TASK_STATUS / ISSUES / HANDOFF 按 §5 路由），并在提交前过 `AGENTS.md §6` 清单。

## 8. 变更控制：要改已经定稿的需求时

已定稿的策略口径、阶段门判据、需求总表条目被要求修改时，过**轻量变更六问**：

1. **改什么**（原口径 → 新口径，逐字写清）；
2. **为什么**（新证据 / 新数据 / 什么问题，证据要可追溯，不接受"感觉"）；
3. **影响面**：哪些策略、数据、脚本、文档、历史结论会跟着动；
4. **挤掉什么**：延迟哪个工单、占多少工时；
5. **谁拍板**：口径、阶段门判据、红线类变更必须用户明确拍板，AI 不自作主张；
6. **登记到哪**：按下表分级。

| 变更级别 | 判据 | 动作 |
|---|---|---|
| 小改 | 措辞、状态、易变数字 | 直接改 + HANDOFF 一行 |
| 中改 | 需求增删、优先级调整、挂起↔激活 | 重过 §4 准入清单 + 改 REQUIREMENTS + 台账联动 |
| 大改 | 北极星、策略因子口径、G 门判据、红线 | **必须写 ADR + 用户明确拍板**；旧结论不删，加 Superseded 注记 |

已验证的历史结论（如 G2 绩效数字）**不回改**，只能被新证据取代；模拟盘复现不了超额不进实盘、成长 Hold 期间不进模拟盘，属门判据，变更走大改。

---

## 9. 需求讨论中的红线（同 AGENTS §4，再强调）

- 不替用户拍板上线/实盘/资金；不替操盘手定扫描器参数（I8）；
- 不自动下单、不给买卖建议、不承诺收益；
- 数据可得性未验证前，不把需求标成"已就绪"；不可得就标"待确认"，不伪造数据填充；
- `09_调研底稿与素材/` 原始素材只读；密钥不入库。
