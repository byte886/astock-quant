# 决策记录 #005 · 全市场扫描计算引擎分工：Polars 主算指标/形态、DuckDB 捞数对账、pandas 保留月频回测

- 关联：ADR-004（Parquet + DuckDB，本 ADR 是其「落地前置：自有数据小基准」的兑现）、T29 / I12 / D-17、`docs/外部代码精读_tickflow扫描器借鉴_2026-09-22.md`
- 证据：`scripts/bench_scan_engines.py`、`results/engine_benchmark/bench_20260922_183240.json`

## 背景

外脑 3 号池扫描器要在**每个交易日对全市场**做"指标计算 + 形态时序判断 + 横截面筛选"。
现有 `scripts/pool3_scan.py` v1 用 pandas 逐只/逐日组织，只会对当天要件"亮灯计数"，缺时序
确认、出场与环境过滤（I12：形似神不似）。T29 要做 v2，D-17 待拍板其中不依赖操盘手阈值的
"A 类纯结构逻辑"。在动手重写前，必须先定"用什么算"。

ADR-004 当初只引入了 DuckDB 做只读查询，把 Polars 列为"暂不引入的候选"，并明确**落地前置**：
扫描读取层切换前，必须在本仓自有 Parquet 上跑一次 DuckDB vs Polars vs pandas 小基准，不采信
外部榜单。本 ADR 兑现该前置；同时参考了对 tick-stock-panel v0.2.2 的只读精读（同代技术栈、
26 个内置形态策略）。

**与 tickflow 的一处关键印证（读代码后修正认知）**：它的形态信号并非用 Polars 直接算，而是
`Parquet（按日分区）→ Polars .over("symbol") 算指标列 → numpy 宽矩阵向量化算信号`。本项目
日频、单机，不需要它为 Web 实时准备的 numpy 宽矩阵 + memmap 缓存重型设施。

## 基准设计（在本仓自有数据上实测）

- 数据：本仓"一只一文件、按市场分目录"的日线 Parquet（`data/raw/daily/{sh,sz}/*.parquet`），
  近 3 年（date ≥ 2023-09-21）＝ **2116 只、1,512,211 行**（全市场下载进行中，当前 2116/4889）。
- 负载（贴近 002 平台突破、扫描器真实链路）：
  - **L1 捞数/IO**：读近 3 年所需 7 列并物化成内存表；
  - **L2 指标**：按 code 分组算 MA20、量比（当日量 / 前 5 日均量，不含当日）、前 10 日最高/最低；
  - **L3 形态时序**：平台突破 ＝ 前 10 日（不含今日）振幅 ≤8% 且 收盘破前 10 日高 且 量比 ≥1.5；
  - **L4 横截面**：最新交易日命中票按量比降序取前 10。
- 三引擎各跑**独立子进程 ×3 次取中位数**（隔离峰值内存），并交叉校验结果。
- 环境：macOS、Python 3.12、pandas 3.0.6、duckdb 1.5.5、polars 1.44.2、pyarrow 25.0.1。

### 结果（中位数，秒；峰值常驻内存 MB）

| 引擎 | L1 捞数 | L2 指标 | L3 形态 | L4 横截面 | 合计 | 相对 | 峰值内存 |
|---|---|---|---|---|---|---|---|
| pandas（逐只 read→concat→groupby） | 3.155 | 1.475 | 0.026 | 0.007 | **4.726** | 1.00× | 1574 |
| DuckDB（read_parquet + 窗口函数 SQL） | 0.201 | 0.375 | 0.035 | 0.003 | **0.614** | 0.13×（快约 7.7 倍） | 1073 |
| **Polars**（lazy scan + `.over("symbol")`） | 0.220 | **0.125** | 0.038 | 0.004 | **0.390** | **0.08×（快约 12 倍）** | **701** |

**一致性校验**：三引擎最新交易日命中均为 22 票、top5 完全相同；历史累计信号 pandas=Polars=24400、
DuckDB=24410（差 0.04%，定位为窗口边界浮点舍入；无重复 K 线）。口径对齐，数字可比。

### 分项解读

- **L1 捞数**：pandas 逐只整文件读全历史再过滤（约 3.2s）；Polars/DuckDB 借 Parquet 行组统计
  做谓词下推，近 3 年窗口只读相关行组（约 0.2s，快约 15 倍）。
- **L2 分组滚动指标（扫描器的主体计算）**：Polars 0.125s 最快且最省内存，比 pandas 快约 12 倍、
  比 DuckDB 快约 3 倍；`.over("symbol")` + rolling 一条表达式算全市场，天然向量化、无逐只循环。
- **L3 形态布尔判断 / L4 横截面**：三者都在毫秒级，**形态判断本身不挑引擎**，不必为此引入 numpy
  宽矩阵。
- **内存**：Polars 701 MB ≈ pandas 1574 MB 的 45%；全市场 4889 只 + 更多指标列 + 分钟数据时，
  列存的内存余量更稳。

## 决策（建议，待用户确认后转 Accepted）

1. **扫描器 v2 的指标/形态批量计算用 Polars**：`pl.scan_parquet(glob)` 懒加载 + 列裁剪/谓词下推，
   `.over("code")` 做分组滚动指标，形态条件用向量化表达式表达"前 N 日窗口 / 近 N 日持续 / 不破前低"，
   替代 pandas 逐只逐日循环。**新增扫描能力默认用 Polars 写。**
2. **DuckDB 维持 ADR-004 定位**：全市场即席 SQL、跨文件/跨源对账、数据质检、临时聚合，一句
   `read_parquet(glob)` 就地查；不承担复杂嵌套形态的主计算（SQL 写"先 A 后 B、N 日内、不创新低"
   可读性差，且 L2 比 Polars 慢约 3 倍）。
3. **pandas 保留在量子月频多因子回测、模拟盘、结果可视化**（`src/quant/`、`src/execution/`）：
   月频 706 只已过 G2、无性能痛点，**不重写**；pandas 仍是最顺手的结果整理/出图层。
4. **三者靠 Parquet / Arrow 互通、同进程并存**，不互斥、不做二选一；不引入 ClickHouse 等常驻服务。
5. **不照搬 tickflow 的 numpy 宽矩阵 + memmap 磁盘缓存**：那是为 Web 多用户实时刷新设计；本项目
   日频盘后扫描，Polars 表达式已足够，避免过度工程（L3 证明形态布尔运算毫秒级）。
6. **暂不另建"全市场长表 / 按日期分区"派生数据集**：现有一只一文件布局下，Polars/DuckDB 的 L1
   已约 0.2s，未到瓶颈，原始一只一文件继续作底稿。触发重评条件见文末。
7. **策略组织借鉴 tickflow 声明式契约**（属 D-17/T29 设计原则，本 ADR 只定范式、不定阈值）：
   每策略一个文件，文件头集中声明参数（含 default/min/max/step，便于 T30 操盘手校准与 B6 参数
   敏感性）、依赖字段、预热棒数（防未来函数），`compute_signals` 纯函数、进场/出场/止损/最长持有
   对称；扫描与回测共用同一信号函数，避免"两套逻辑"。**所有阈值仍以操盘手 T30 通达信校准为准，
   tickflow 默认值仅候选、不直接采用。**
8. `polars` 加入 `requirements.txt`（随本 ADR 转 Accepted 后成为正式依赖；当前基准脚本已需要）。

## 备选（被放弃的）

- **扫描器继续全 pandas**：当前 4.7s 绝对耗时虽不算日频瓶颈，但逐只循环 + 形态时序靠手写 shift
  累积，可维护性差（I12 根因），内存最高，全市场 + 分钟 + 多策略扩展余量小。
- **全 DuckDB SQL（含形态）**：捞数/聚合优秀，但复杂嵌套形态与"状态机式"条件用 SQL 表达绕、难
  调试，L2 也慢于 Polars；让 SQL 做它擅长的捞数/对账即可。
- **照搬 tickflow numpy 宽矩阵 + memmap**：性能极致但工程复杂度高（停牌 ValidBarIndex、磁盘缓存
  指纹/预热），为我们不需要的 Web 实时买单，违背个人单机轻量原则。
- **换 qlib / vn.py / Backtrader 等框架承载扫描**：Q3 已决策自研 pandas 轻量引擎、不引重型框架；
  Polars/DuckDB 都是进程内本地库，与该决策不冲突。

## 已知局限 / 诚实清单

- **性能不是"现在 pandas 跑不动"**：近 3 年 2116 只 pandas 合计 4.7s，日频扫描远未到非功能红线
  （日增量 ≤1 小时）。换 Polars 的首要收益是**形态时序的表达力/可维护性、内存余量与全市场/分钟
  扩展天花板**，速度是加分项；不要为了用新技术而重写已稳定的月频回测。
- 基准只覆盖**一个代表性形态 + 基础指标**，未含板块共振、流通市值、财务门槛（003）、停牌 valid_shift
  等真实扫描器全部环节；扫描器 v2 落地后应以**真实全流程**复测一次，再固化。
- 数据仅 2116/4889 只且下载进行中；**全市场下完后重跑 `bench_scan_engines.py`**，确认规模放大后
  结论与内存余量是否仍成立（尤其 L1 文件数翻倍、未来分钟级形态）。
- DuckDB 与 pandas/Polars 历史累计信号有 0.04% 边界差异（横截面当日完全一致）；实盘以单一引擎
  （Polars）产出信号，避免多引擎混用导致口径漂移。
- Polars 是新 API（表达式/lazy 范式与 pandas 不同），有学习成本；使用者为用户 + AI，AI 可代写，
  关键扫描代码需配注释与对照测试，并保留三引擎一致性基准作为回归。
- 本 ADR 只定计算引擎与策略骨架范式，**不替操盘手定任何买卖阈值、不改变 001/002/003 规则**。

## 后果 / 何时重新评估

- 用户确认（转 Accepted）后：T29 的 A 类结构逻辑用 Polars 落地扫描器 v2 骨架；同步把
  `polars` 从评估依赖转正；`pool3_scan.py` 的 pandas 旧实现保留至新链路与通达信校准（T30）对齐后再退役。
- 全市场日线下载完成后重跑基准与全流程复测；结果记入 T29 验收。
- 若出现以下情况，重评"是否建按日期分区/长表派生数据集"或引入 numpy 宽矩阵：
  ① 全市场 4889 只 + 全指标列下单日扫描 L1+L2 超过数分钟；② 形态复杂到 Polars 表达式可读性显著
  下降；③ 分钟级形态成为主负载；④ 需要盘中近实时刷新（当前明确不做）。
- 若 Polars 在真实复杂形态上不及预期，可退回"DuckDB 捞数 + pandas 算"的组合，基准脚本可随时复跑对比。
